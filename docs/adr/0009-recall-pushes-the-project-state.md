# Recall pushes the project's state; the device never wins

When a DAW project opens, each plugin instance pushes its saved state to the INTEGRA-7 through the [Device service](0006-device-service-owns-the-link.md). Nothing is compared or merged first, so an edit made on the device outside the DAW is lost. The Studio Set is recalled by the Studio Set plugin pushing its own blocks into the temporary Studio Set, never by loading a stored Studio Set by number. Decided in [Recall device state from the DAW project](https://github.com/sigma/integral/issues/344).

## Considered Options

- **The device wins.** Rejected: the point of recall is that reopening a project brings its sound back.
- **Read back, diff, then ask.** Rejected: it costs an RQ1 round trip per block within a 25 DT1/s budget, and the prompt would repeat across up to 16 instances. The device sends DT1 only in reply to RQ1, so without polling the service can't tell that the device changed anyway ([#343](https://github.com/sigma/integral/issues/343)).
- **Load the Studio Set by number.** Rejected: it overwrites every Part in bulk, so it races the Tone and Kit pushes, and the stored set may have changed since the project was saved.
- **A tone by reference (Bank Select and PC) only.** Rejected: unsaved tone edits would be lost, and a User slot may hold another tone by now.

## Consequences

- **Tone and Kit plugins save the tone selection and its name** beside their host parameters. On recall they send the selection first, then the tone's values. Because the saved type is restored with the tone, a type mismatch can't arise on recall.
- **Preset and Expansion tones push only their differences.** Those tones never change, so the tone as the device reported it right after selection is a reliable baseline. The service keeps that snapshot. Recall sends the selection, asks for the baseline, and sends one DT1 per run of fields that differ from it, joined over the baseline's own bytes where they lie between two changes (about one DT1 per block of the tone). An untouched preset is one message instead of about 25. When the diff would take more DT1s than the full runs, the plugin pushes the full runs instead. If the baseline names another tone the selection is sent again; with no baseline the full runs go. Both are formed in the plugin, because the service's device queue holds one item at a time, so nothing downstream could merge a field-by-field filter's survivors.
- **GM2 and ExPCM tones push their selection alone.** The device does not let one edit them or read them back.
- **User tones always push in full.** A User slot can be overwritten after the project is saved, so a diff against it would give the wrong sound. The Studio Set plugin also pushes in full: it never loads a set by number, so it has no baseline. Full pushes join runs only over bytes proven on hardware to ignore a write (two bytes of the Studio Set Common, [`docs/midi/99-undocumented.md`](../midi/99-undocumented.md)), written as 0, and never over a Part's tone-select bytes. The other `<*>` bytes of the MIDI Implementation are not bridged: some took a write, and the rest were not tried.
- **Each byte has one owner.** The Studio Set plugin pushes Common, Chorus, Reverb, Master EQ, Motional Surround, each Part's mixer fields, Part EQ and Drum COMP+EQ, but never the Part tone-select bytes (`00 06`–`00 08`). Only the Tone or Kit plugin bound to a Part sends those. Pushes from different instances therefore don't depend on order.
- **A Kit plugin bound to a key sends only that key's fields.** It never selects: the Part's kit belongs to the plugin bound to the whole kit, and a selection reloads every key. So when another writer's tone change reaches the Part after the key plugin has pushed, and the Part still holds the kit it saved, it pushes again instead of adopting the reloaded kit (a few times at most per session).
- **What a project doesn't cover stays as the device holds it.** A project with no Studio Set plugin leaves the Studio Set alone, and a Part with no Tone or Kit plugin keeps its tone.
- **A fresh instance adopts the device.** With no saved state it reads its bound blocks and sets its parameters silently. Dropping a plugin onto a track never changes the sound.
- **Push on load, on every restore and on every new device session.** The service gives each link session an ID; it changes when the link drops, the device power-cycles or the service restarts. An instance that holds a state it trusts pushes once per session ID. A socket drop within one session pushes nothing. A state the host restores in the middle of a session (a DAW preset, a revert, a hot swap) is pushed as well.
- **The project, the host's state, always wins.** An instance trusts the state the host restored, and the state it adopted from the device and has held since: the project is what the DAW holds, edits made in the DAW included. So only a brand-new instance's first session adopts; in every later session (a power cycle, say) the device gets what the instance holds. A restored Tone or Kit instance that saved no valid tone has nothing to select and adopts from the start. Binding the instance to another target by hand pushes nothing there: the instance adopts the new target.
- **A tone picked in the editor just before a push becomes owed** (the editor offers no pick while one is owed, but it learns of that late) stands if only the device session is new: the pick is the user's latest word, so the instance saves it and pushes nothing over it in that session. If a host restore made the push owed, the restore is the later act and the project's, so it wins: the push selects the restored tone over the pick. A pick that reaches the Part while the push is under way makes the push start over from its selection, so no tone is left with another's values ([#504](https://github.com/sigma/integral/issues/504)).
- **The push sends current values**, read when it is queued, not the snapshot as saved: automation the host applied or a knob moved while offline is included.
- **Pacing.** The plugin sends only the fields it has parameters for, as DT1s over runs of adjacent fields, so the gaps cost messages: a User PCM Synth tone is 26 DT1s (about 1 s at 40 ms each), so 16 such Parts pushed in full take about 17 s, and the Studio Set is 136 DT1s, about 5.5 s more. Untouched presets bring 16 Parts under a second once the service has read each preset before (it keeps what it read for the life of the process). Cold, every distinct preset is read back first, a block at a time in its client's turns: about 2 s until the first write goes out and about 7 s until all 16 baselines exist. The service serves clients round-robin, so every Part fills in progressively. A write queued after a push always lands after it.
- **No gating.** Notes and transport run during recall, and a Part may sound wrong for its first seconds. Each instance shows "Recalling…" until its push has gone out, and "Device offline" while it waits for a session.
- **Duplicate Bindings:** both instances push, and their pushes interleave item by item, so the device may end up with a mix of the two. They already warn ([ADR 0006](0006-device-service-owns-the-link.md)).
